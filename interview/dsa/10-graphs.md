# 10. Graphs: BFS, DFS, topological sort, Dijkstra, union-find

A tree has one path between any two nodes. Most real relationships don't: roads loop back,
packages depend on several others, a course has more than one prerequisite. Once there can be
several paths, or cycles, the questions change. Which path is shortest? Is there an order that
respects every dependency? Are these two things connected at all? Graph algorithms answer those
questions, and a handful of them (the five in this chapter's title) cover nearly everything an
interview will ask.

## 10.1 Representing a graph

A **graph** is a set of **vertices** (nodes) and **edges** between them. Edges may be
**directed** (a → b) or **undirected**, and may carry a **weight** (a distance, a cost). V is the
number of vertices and E the number of edges.

| Representation | Memory | "Neighbours of u" | "Is there an edge u–v?" | Use when |
|---|---|---|---|---|
| **Adjacency list**: `adj[u]` = list of neighbours | O(V + E) | O(degree of u) | O(degree of u) | almost always |
| **Adjacency matrix**: `m[u][v]` = edge or not | O(V²) | O(V) | O(1) | dense graphs, V ≤ a few thousand |
| **Implicit**: a grid, or states generated by rules | none stored | computed on the fly | computed | grids, puzzles, word ladders |

Interview problems usually give an edge list, and the first few lines turn it into an adjacency
list:

```go
adj := make([][]int, n)
for _, e := range edges { // undirected: add both directions
	adj[e[0]] = append(adj[e[0]], e[1])
	adj[e[1]] = append(adj[e[1]], e[0])
}
```

Grids are graphs too: each cell is a vertex, and its up/down/left/right neighbours are its edges.
Recognising a grid problem as a graph problem is often the whole insight.

## 10.2 Breadth-first search: shortest paths by step count

### The intuition

Drop a stone in a pond. The ripple reaches everything one step away, then everything two steps
away, and so on. BFS does exactly that with a queue: it visits vertices in order of their
distance (in edges) from the start. So **the first time BFS reaches a vertex, it has found a
shortest path to it**, in an unweighted graph.

### Counting islands in a grid

Count the islands (connected groups of `'1'` cells) in a grid. Scan every cell; each time you
find unvisited land, that's a new island, and BFS from it marks the whole island visited.

```go
func numIslands(grid [][]byte) int {
	rows, cols := len(grid), len(grid[0])
	dirs := [4][2]int{{1, 0}, {-1, 0}, {0, 1}, {0, -1}}
	count := 0
	for r := range rows {
		for c := range cols {
			if grid[r][c] != '1' {
				continue
			}
			count++
			grid[r][c] = '0' // mark on push, not on pop
			queue := [][2]int{{r, c}}
			for len(queue) > 0 {
				cur := queue[0]
				queue = queue[1:]
				for _, d := range dirs {
					nr, nc := cur[0]+d[0], cur[1]+d[1]
					if nr >= 0 && nr < rows && nc >= 0 && nc < cols && grid[nr][nc] == '1' {
						grid[nr][nc] = '0'
						queue = append(queue, [2]int{nr, nc})
					}
				}
			}
		}
	}
	return count
}
```

This marks visited cells by overwriting the input. That's normal on LeetCode, but say it out
loud in an interview ("I'll mutate the grid; if that's not allowed I'll keep a `visited`
array"), because modifying a caller's data is a design decision.

**Complexity:** every cell is enqueued at most once and checks 4 neighbours: O(rows × cols) time
and, in the worst case, the same space for the queue. For a general graph, BFS is **O(V + E)**:
each vertex is dequeued once, and each edge is examined once (twice if undirected).

> ⚠️ **Mark a vertex visited when you push it, not when you pop it.** If you mark on pop, a vertex
> can be pushed once by each neighbour before it's first popped. The answer is usually still
> right, so tests pass, but the queue holds up to one entry per *edge* rather than per vertex,
> and each duplicate is expanded again unless you also check on pop. On a grid that's at most 4×
> the work; on a dense graph, where E approaches V², it's the difference between passing and
> timing out. Marking on push guarantees each vertex enters the queue exactly once.

**Multi-source BFS.** "Rotting oranges" (every rotten orange infects its neighbours each minute)
is BFS started from *all* rotten oranges at once: put them all in the queue at distance 0. The
ripples spread in parallel, and the distance at which a cell is first reached is the minute it
rots.

## 10.3 Depth-first search

DFS goes as deep as possible before backing up: the recursion from
[file 07](07-recursion-and-backtracking.md), on a graph, with a `visited` set so that cycles
don't trap it. It doesn't find shortest paths, but it's the natural tool for:

- **Connected components:** same as islands; DFS or BFS both work.
- **Cycle detection in a directed graph:** colour each vertex *white* (unvisited), *grey* (on the
  current DFS path) or *black* (finished). Meeting a grey vertex means you've found an edge back
  into your own path: a cycle. Meeting a black one is fine; it's a different, finished branch.
- **Path existence**, and anything where you explore, mark, and possibly unmark (backtracking on
  a grid, as in Word Search).

Same O(V + E). Recursive DFS on a graph of 10^5 vertices can be 10^5 deep; see the stack limits
in [file 01 §1.4](01-foundations.md#space-complexity), and switch to an explicit stack if needed.

## 10.4 Topological sort: an order that respects dependencies

### The problem

Courses have prerequisites. Is there an order to take them all, and if so, what is it? More
generally: given a directed graph of "a must come before b", produce a linear order, or report
that a cycle makes it impossible.

### The intuition (Kahn's algorithm)

Start with everything that has **no** remaining prerequisites; those can be done now. Do one,
and cross it off as a prerequisite of everything that depended on it. Anything whose last
prerequisite just got crossed off becomes available. Repeat. If you run out of available items
before doing everything, the leftovers are waiting on each other: a cycle.

The count of remaining prerequisites is the vertex's **in-degree**. A. B. Kahn published this in
1962 (*Topological sorting of large networks*, Communications of the ACM 5(11)).

```go
// topoOrder returns an order of 0..n-1 respecting every edge u->v, or nil if there is a cycle.
func topoOrder(n int, edges [][2]int) []int {
	adj := make([][]int, n)
	indeg := make([]int, n)
	for _, e := range edges {
		adj[e[0]] = append(adj[e[0]], e[1])
		indeg[e[1]]++
	}
	queue := []int{}
	for v := range n {
		if indeg[v] == 0 {
			queue = append(queue, v)
		}
	}
	order := []int{}
	for len(queue) > 0 {
		u := queue[0]
		queue = queue[1:]
		order = append(order, u)
		for _, v := range adj[u] {
			indeg[v]--
			if indeg[v] == 0 { // last prerequisite done
				queue = append(queue, v)
			}
		}
	}
	if len(order) < n {
		return nil // some nodes never reached in-degree 0: they sit on a cycle
	}
	return order
}
```

Edges `0→1, 0→2, 1→3, 2→3`:

```
in-degree at start: [0, 1, 1, 2]        queue: [0]
pop 0 → order [0];        1: 1→0 push, 2: 1→0 push     queue: [1, 2]
pop 1 → order [0,1];      3: 2→1                        queue: [2]
pop 2 → order [0,1,2];    3: 1→0 push                   queue: [3]
pop 3 → order [0,1,2,3]                                  queue: []
4 of 4 ordered → no cycle
```

**Complexity:** O(V + E). There can be many valid orders (here `[0, 2, 1, 3]` too); problems that
want a specific one, such as the lexicographically smallest, swap the queue for a min-heap.

> ⚠️ **Get the edge direction right before anything else.** LeetCode 207 gives
> `[a, b]` meaning "to take a you must first take b", so the edge is **b → a**. Build it the other
> way round and you get a valid order of the *reversed* graph, which is the reverse of what was
> asked. The cycle detection still works, which is why this survives the yes/no version and fails
> the version that asks for the order.

## 10.5 Weighted shortest paths: Dijkstra

### The problem

Edges have non-negative weights (travel times, latencies). Find the shortest distance from a
source to every vertex. BFS doesn't work any more: the path with fewest edges isn't necessarily
the cheapest.

### The intuition

> **Teacher's aside.** Dijkstra's algorithm is BFS with the queue replaced by a priority queue.
> BFS settles vertices in order of *edge count*; Dijkstra settles them in order of *distance*,
> always expanding the closest unsettled vertex next. Why is the closest one safe to settle? Any
> other route to it would have to pass through some vertex that's currently further away, and
> since weights are non-negative, continuing from there can only make the route longer. That one
> sentence is the whole correctness argument, and it's also exactly why **negative weights
> break it**: a negative edge could make a long detour come out cheaper after you've already
> declared the vertex settled.

Edsger Dijkstra published it in 1959 (*A note on two problems in connexion with graphs*,
Numerische Mathematik 1). The version below is the one everyone writes in interviews: a binary
heap, with **lazy deletion**. When a vertex's distance improves you push a new entry rather than
updating the old one (binary heaps can't find entries cheaply), and when an outdated entry is
popped later, you skip it.

```go
type Edge struct{ To, W int }
type item struct{ node, dist int }
type distHeap []item

func (h distHeap) Len() int           { return len(h) }
func (h distHeap) Less(i, j int) bool { return h[i].dist < h[j].dist }
func (h distHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *distHeap) Push(x any)        { *h = append(*h, x.(item)) }
func (h *distHeap) Pop() any {
	old := *h
	x := old[len(old)-1]
	*h = old[:len(old)-1]
	return x
}

// dijkstra returns shortest distances from src; math.MaxInt means unreachable.
// All weights must be non-negative.
func dijkstra(adj [][]Edge, src int) []int {
	dist := make([]int, len(adj))
	for i := range dist {
		dist[i] = math.MaxInt
	}
	dist[src] = 0
	h := &distHeap{{src, 0}}
	for h.Len() > 0 {
		cur := heap.Pop(h).(item)
		if cur.dist > dist[cur.node] {
			continue // stale entry: we already found a shorter way here
		}
		for _, e := range adj[cur.node] {
			if nd := cur.dist + e.W; nd < dist[e.To] {
				dist[e.To] = nd
				heap.Push(h, item{e.To, nd})
			}
		}
	}
	return dist
}
```

```rust
use std::cmp::Reverse;
use std::collections::BinaryHeap;

fn dijkstra(adj: &Vec<Vec<(usize, u64)>>, src: usize) -> Vec<u64> {
    let mut dist = vec![u64::MAX; adj.len()];
    dist[src] = 0;
    let mut heap = BinaryHeap::new();
    heap.push(Reverse((0u64, src))); // (distance, node), smallest distance first
    while let Some(Reverse((d, u))) = heap.pop() {
        if d > dist[u] {
            continue; // stale entry
        }
        for &(v, w) in &adj[u] {
            let nd = d + w;
            if nd < dist[v] {
                dist[v] = nd;
                heap.push(Reverse((nd, v)));
            }
        }
    }
    dist
}
```

Tuples compare field by field, so putting the distance first makes it the sort key, and
`Reverse` turns Rust's max-heap into the min-heap Dijkstra needs.

### Worked example

Edges `0→1 (4)`, `0→2 (1)`, `2→1 (2)`, `1→3 (1)`, `2→3 (5)`; vertex 4 has no edges in.

```
pop        stale?   relax                                  dist [0,1,2,3,4]     heap after
(0, 0)     no       1: 0+4=4 ✓, 2: 0+1=1 ✓                 [0, 4, 1, ∞, ∞]      (1,2) (4,1)
(1, 2)     no       1: 1+2=3 < 4 ✓, 3: 1+5=6 ✓             [0, 3, 1, 6, ∞]      (3,1) (4,1) (6,3)
(3, 1)     no       3: 3+1=4 < 6 ✓                         [0, 3, 1, 4, ∞]      (4,1) (4,3) (6,3)
(4, 1)     yes: 4 > dist[1]=3, skip                                              (4,3) (6,3)
(4, 3)     no       (no outgoing edges)                                          (6,3)
(6, 3)     yes: 6 > 4, skip
result: [0, 3, 1, 4, unreachable]
```

The direct edge 0→1 (cost 4) loses to the detour 0→2→1 (cost 3): exactly what BFS would miss.

**Complexity:** each edge can push one entry, so the heap holds at most E + 1 entries, and every
push and pop costs O(log E) = O(log V) (since E ≤ V²). Total **O((V + E) log V)**. With a
Fibonacci heap it's O(E + V log V) (Fredman and Tarjan, *Fibonacci heaps and their uses in
improved network optimization algorithms*, JACM 1987), which matters in theory and rarely in
practice; nobody expects you to write one.

> ⚠️ **Negative weights break Dijkstra, and how they break it depends on the version.** The
> textbook algorithm marks a vertex *settled* when it's first popped and never revisits it. With
> a negative edge that returns wrong distances, silently: on `A→B 2, A→C 3, C→B −2` it reports
> B = 2, and the truth is 1. The lazy version above has no settled set, so when C later improves
> B it re-pushes B and re-expands it. I ran both: the lazy one returned the correct 1. That isn't
> a licence to use it. It's no longer Dijkstra's algorithm, it loses the O((V + E) log V) bound
> (vertices can be re-expanded many times), and a negative *cycle* makes it run forever. With
> negative edges use Bellman–Ford, O(VE), which also detects negative cycles. For a *limit on the
> number of edges* ("at most k stops", LeetCode 787), Dijkstra on distance alone is also wrong,
> because a cheaper path with too many stops can block a valid dearer one; run Bellman–Ford for
> k + 1 rounds, or put the stop count into the state.

## 10.6 Union-find: are these connected?

### The problem

Edges arrive one at a time. After each, you need to answer "are u and v connected?" or "did this
edge just create a cycle?". Re-running BFS after every edge costs O(V + E) each time.

### The intuition

Think of clubs that each have a president. To know whether two people are in the same club, ask
each of them for their president and compare. To merge two clubs, one president agrees to report
to the other. That's a **disjoint-set union (DSU)**, or **union-find**: a forest where each set
is a tree, and the root is its representative.

Two tricks keep the trees almost flat:

- **Union by rank:** hang the shorter tree under the taller one, so height grows only when two
  equal-height trees merge.
- **Path compression:** whenever you walk up to find a root, repoint nodes along the way closer
  to the root, so the next walk is shorter. The code below uses **path halving**, which points
  every other node at its grandparent in a single pass, with no recursion.

```go
type DSU struct{ parent, rank []int }

func NewDSU(n int) *DSU {
	d := &DSU{make([]int, n), make([]int, n)}
	for i := range d.parent {
		d.parent[i] = i
	}
	return d
}

func (d *DSU) Find(x int) int {
	for d.parent[x] != x {
		d.parent[x] = d.parent[d.parent[x]] // path halving: point at grandparent
		x = d.parent[x]
	}
	return x
}

// Union merges the sets holding a and b; false means they were already together.
func (d *DSU) Union(a, b int) bool {
	ra, rb := d.Find(a), d.Find(b)
	if ra == rb {
		return false
	}
	if d.rank[ra] < d.rank[rb] {
		ra, rb = rb, ra
	}
	d.parent[rb] = ra // shorter tree hangs under the taller one
	if d.rank[ra] == d.rank[rb] {
		d.rank[ra]++
	}
	return true
}
```

```rust
struct Dsu {
    parent: Vec<usize>,
    rank: Vec<u8>,
}

impl Dsu {
    fn new(n: usize) -> Self {
        Dsu { parent: (0..n).collect(), rank: vec![0; n] }
    }
    fn find(&mut self, mut x: usize) -> usize {
        while self.parent[x] != x {
            self.parent[x] = self.parent[self.parent[x]];
            x = self.parent[x];
        }
        x
    }
    fn union(&mut self, a: usize, b: usize) -> bool {
        let (mut ra, mut rb) = (self.find(a), self.find(b));
        if ra == rb {
            return false;
        }
        if self.rank[ra] < self.rank[rb] {
            std::mem::swap(&mut ra, &mut rb);
        }
        self.parent[rb] = ra;
        if self.rank[ra] == self.rank[rb] {
            self.rank[ra] += 1;
        }
        true
    }
}
```

`find` takes `&mut self` because it rewrites parents as it goes; a "read-only" lookup that
mutates is something Rust makes you admit to.

struct DSU {
    vector<int> parent, rnk;
    DSU(int n) : parent(n), rnk(n, 0) { iota(parent.begin(), parent.end(), 0); }
    int find(int x) {
        while (parent[x] != x) {
            parent[x] = parent[parent[x]];
            x = parent[x];
        }
        return x;
    }
    bool unite(int a, int b) {  // `union` is a C++ keyword
        int ra = find(a), rb = find(b);
        if (ra == rb) return false;
        if (rnk[ra] < rnk[rb]) swap(ra, rb);
        parent[rb] = ra;
        if (rnk[ra] == rnk[rb]) ++rnk[ra];
        return true;
    }
};

### How fast, really

With both union by rank and path compression, a sequence of m operations on n elements costs
O(m · α(n)), where α is the inverse Ackermann function: **amortised O(α(n)) per operation**.
Tarjan proved the bound in 1975 (*Efficiency of a good but not linear set union algorithm*,
JACM 22(2)), and Tarjan and van Leeuwen (JACM 31(2), 1984) showed that one-pass variants such as
path halving achieve it too. α(n) grows so slowly that it's at most 4 for any n you could store
in a computer, so in conversation "effectively constant" is fair. Saying "O(1)" outright isn't
quite right, and an interviewer who asks will want to hear "inverse Ackermann".

With only one of the two tricks, the bound is O(log n) per operation; with neither, a chain of
unions can produce an O(n)-tall tree.

### Where it's used

- **Redundant connection:** add edges one by one; the first `Union` that returns `false` joins two
  vertices that were already connected, so that edge closes a cycle.
- **Number of components:** start with n, subtract one for every successful `Union`.
- **Kruskal's minimum spanning tree:** sort edges by weight, add each one unless it would make a
  cycle.
- Anything with "groups that merge over time" (accounts sharing an email, equations of equal
  variables). Union-find can't *split* groups; if edges are deleted, you need something else.

## 10.7 Choosing the algorithm

| The question | Graph | Use | Time |
|---|---|---|---|
| Fewest steps from A to B | unweighted | BFS | O(V + E) |
| Fewest steps from any of several starts | unweighted | multi-source BFS | O(V + E) |
| Is everything connected / count components | undirected | BFS, DFS or union-find | O(V + E) |
| Connectivity as edges keep arriving | undirected | union-find | O(α(n)) amortised per op |
| An order respecting dependencies; detect a cycle | directed | topological sort (Kahn) | O(V + E) |
| Cheapest path, non-negative weights | weighted | Dijkstra | O((V + E) log V) |
| Cheapest path with negative weights, or with at most k edges | weighted | Bellman–Ford (k rounds) | O(VE), or O(kE) |
| Shortest paths between all pairs, V ≤ ~400 | weighted | Floyd–Warshall | O(V³) |
