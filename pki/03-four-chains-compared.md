# 3. Four chains, compared

Assumes files [01](01-what-a-certificate-is.md) and [02](02-building-and-walking-a-chain.md).

## The problem

Files 01 and 02 are scheme-agnostic on purpose: path validation is the same arithmetic
everywhere. That universality is genuinely useful and it is also a trap, because it invites
the conclusion that *verifying a chain* means the same thing everywhere.

It doesn't. Four chains you are likely to meet in one career use identical machinery to answer
four different questions, and the differences are almost entirely in the two places RFC 5280
has nothing to say about: **where the anchor came from**, and **what the names mean**.

This chapter puts them side by side. It's also the chapter that corrects the most common
cross-domain mistake — assuming that because an Android app has a signing certificate, that
certificate has an issuer CA. It does not, and §3.4 is about why.

## 3.1 Web TLS — "does this key control that domain name?"

```
  ~100+ roots in the OS/browser store      ← shipped with your operating system
       │
  intermediate (sent by the server)
       │
  leaf: SAN = example.com                   ← sent by the server
```

| | |
|---|---|
| **Asserts** | the key holder demonstrated control of a DNS name, at issuance time |
| **Issuer** | one of many commercial CAs, each able to issue for **any** name |
| **Anchor from** | your operating system's trust store — a file on disk, found by a hardcoded path list |
| **Subject name means** | a DNS name, in `subjectAltName`. The `commonName` is dead for this purpose |
| **Revocation** | OCSP/CRL, widely soft-failed in practice |

The structural weakness is in the second row: any trusted CA may vouch for any name, so the
system's integrity is that of its *weakest* member. Certificate Transparency doesn't prevent
misissuance, it makes it findable after the fact.

Covered properly in [`http/05`](../http/05-certificates-and-trust.md) — including the three
questions a TLS client asks, where the trust store actually lives, and why a minimal container
image trusts nothing. CT is in [`signatures/02`](../signatures/02-trust-anchors.md) §2.5.

## 3.2 An eID card's authentication certificate — "who is this person?"

```
  CSCA / national root                      ← obtained OUT OF BAND, pinned by fingerprint
       │
  (sometimes one issuing CA)
       │
  leaf: subject = a named human             ← read off the card
```

| | |
|---|---|
| **Asserts** | a state's claim that this key belongs to a named, enrolled person |
| **Issuer** | one authority — but typically several live CAs at once, across key changeovers |
| **Anchor from** | the issuer directly, through a channel that isn't the card. For travel documents, a **CSCA master list**; in the EU, the eIDAS **List of Trusted Lists** |
| **Subject name means** | a person, in a national namespace |
| **Revocation** | OCSP or CRL, and here it is genuinely load-bearing — cards get lost |

Two things make this different from §3.1 rather than just smaller.

**The anchor is deliberately not a general trust store.** You want *this* issuer and nobody
else, so the anchor is pinned rather than inherited from the OS. ICAO's answer for passports is
distribution by diplomatic exchange or by signed master lists — a list of CSCA certificates
from states the publisher has a bilateral agreement with
([ICAO PKD](https://www.icao.int/icao-pkd/icao-master-list)). The EU's answer for qualified
certificates is a signed meta-list: the LOTL points at each member state's trusted list, each
list carrying the trust anchors needed to verify the next. In both cases the anchor arrives by
a mechanism *outside* the PKI it anchors — which is file 01 §1.6 with a diplomatic bag.

**The chain is not the proof of genuineness.** A certificate read off a card is copyable, so
chaining it proves the card's *issuer*, never the card. The clone detection is a separate
mechanism: the card signs a fresh challenge with a key it cannot export.
[`smartcards/06`](../smartcards/06-proving-genuineness.md) is that argument;
[`smartcards/07`](../smartcards/07-verifying-the-card-certificate.md) is the chain mechanics,
in more depth than anything in this course.

## 3.3 Android key attestation — "where does this key live?"

```
  Google attestation root                   ← published by Google, fixed, pinned
       │
  intermediate(s)                           ← with RKP, short-lived
       │
  leaf: subject = CN=Android Keystore Key   ← generated by the TEE, carries an EXTENSION
```

| | |
|---|---|
| **Asserts** | this key was generated inside certified secure hardware, on a device in *this* boot state |
| **Issuer** | the device's secure environment, certified up to Google |
| **Anchor from** | Google, published at `https://android.googleapis.com/attestation/root` |
| **Subject name means** | **nothing.** It is the fixed string `CN=Android Keystore Key` on every attestation leaf ever issued |
| **Revocation** | a JSON status list Google publishes, keyed by certificate serial |

That third-from-last row is the one that reframes everything. AOSP specifies the attestation
leaf's `subject` as a constant and its `serialNumber` as the integer `1` on every certificate
([AOSP, Key and ID attestation](https://source.android.com/docs/security/features/keystore/attestation)).
The fields that files 01 and 02 treat as the payload are *deliberately empty of information*.

The payload is in an X.509 **extension**, OID `1.3.6.1.4.1.11129.2.1.17`, holding a
`KeyDescription` that describes the key's properties, the challenge the verifier supplied, and
the device's verified-boot state. The chain's job is only to establish that a certified secure
environment said it. Everything you actually wanted to know is in the extension, and
[`android/11`](../android/11-key-attestation-in-depth.md) is the field-by-field reading of it —
including the distinction that decides what you may believe.

> **Teacher's aside.** Three of these four chains answer **"who is this?"** Attestation answers
> **"where does this key live?"** — a question about provenance, not identity. That is why its
> subject name is blank: there is no person or host to name. The subject of the sentence is the
> *key*, and the predicate is "was born in hardware that a root I trust has certified".
>
> Once you see that, the overlap with §3.2 gets sharper rather than vaguer, because the two
> schemes turn out to be the same two-part design. In both, a **chain** establishes provenance
> against an out-of-band anchor, and a **fresh challenge signed now** establishes that the
> thing in front of you holds the key. A card's certificate chains to a state and the card
> signs your nonce; an attestation chains to Google and the attested key signs your nonce. Get
> one of the two parts and you have half a system: chain without challenge accepts a copied
> certificate, challenge without chain accepts a key the attacker generated in software. The
> pairing is the invariant, and it is worth more than any individual scheme's details.

## 3.4 APK signing — the one that is not a chain

An Android app's signing certificate looks like the other three. It is X.509, it has a subject,
an issuer, a validity period and a signature. Almost every instinct files 01 and 02 built is
wrong about it.

**It is self-signed, and there is no CA.** Android has never required apps to be signed by an
authority: AOSP's app-signing documentation describes self-signed certificates that developers
generate themselves, and in a self-signed certificate `issuer` equals `subject` — so "the issuer
CA of an APK signing certificate" names the developer's own key. There is nothing above it.
Nothing to chain to. No list of issuer CAs to collect.

Public code-signing CAs don't help either, and increasingly can't: the CA/Browser Forum caps
publicly trusted code-signing certificate lifetimes, while Google Play requires an app signing
key's certificate to stay valid past **22 October 2033**. The lifetimes are incompatible by
design, because the two systems are solving different problems.

**So what replaces the chain?** You pin the key. The relying party stores the SHA-256 digest of
the signing certificate and compares. That is the "out-of-band comparison" row of
[`signatures/02`](../signatures/02-trust-anchors.md) §2.2 — the oldest and simplest anchor
there is, with no hierarchy at all.

**What the certificate's fields are for**, then:

| Field | In a CA-issued certificate | In an APK signing certificate |
|---|---|---|
| `issuer` | names the vouching key | names itself. Carries no information |
| `validity` | when the issuer's claim applies | a formality — Android does not expire apps on it, and Play enforces a *minimum* far future date |
| `subject` | who the key belongs to | whatever the developer typed into `keytool` |
| the public key | the thing being vouched for | **the entire point.** The certificate is a container for it |

> ⚠️ This is the cross-domain mistake worth inoculating against: having worked with eID or TLS
> chains, it is natural to assume an app's signing certificate must chain to *something*, and to
> go looking for "the issuer CAs" so you can run a chain check on it. There are none, and a
> chain check is not the control you want. The control is a **pinned digest**. If you find
> yourself collecting issuer CAs for app signing certificates, you have imported a mechanism
> from a system that needed it into one that doesn't.
>
> There *is* a real chain-check problem in the Android picture — it's the attestation chain of
> §3.3, which is a completely separate chain terminating at Google rather than at any app
> developer. Keeping those two apart is most of
> [`android/11`](../android/11-key-attestation-in-depth.md).

**The one hierarchy that does exist** is v3 **signing lineage**: a proof that a new signing key
was endorsed by the old one, so an app can rotate keys without becoming a different app
([`android/03`](../android/03-signing-is-identity.md) §3.2). It is a chain in the sense of being
a linked sequence of signatures, and it is *not* a certification path: there is no authority, no
`basicConstraints`, and nothing it terminates at other than the key you already pinned. Rotation
proof, not vouching hierarchy.

## 3.5 Side by side

| | **Web TLS** | **eID card** | **Android attestation** | **APK signing** |
|---|---|---|---|---|
| Question answered | does this key control that domain? | who is this person? | where does this key live? | was this app built by the same party as last time? |
| Depth | 2–4 | 1–3 | 3–4 | **1** (self-signed) |
| Issuer | any of many commercial CAs | one state authority, several live CAs | the device's TEE, certified to Google | nobody |
| Anchor from | the OS trust store | the issuer, out of band; master lists / LOTL | Google, published | **you** — a pinned digest |
| Anchor count | hundreds | a handful, per scheme | two, currently | one per app |
| "Any CA can vouch for any name" | **yes** — the core weakness | no | no | n/a |
| Subject name carries meaning | yes (SAN) | yes (a person) | **no** (constant string) | no (free text) |
| Payload lives in | the name | the name | an **extension** | the public key |
| Expiry is meaningful | yes | yes | partly — pre-2021 factory certs are expired and still trusted | no |
| Revocation | OCSP/CRL, soft-fail | OCSP/CRL, load-bearing | Google's JSON status list | key rotation via lineage |
| Needs a fresh challenge too | yes (TLS `CertificateVerify`) | **yes** (sign a nonce) | **yes** (`attestationChallenge`) | no — verified at install |

## 3.6 What generalises, and what doesn't

Worth separating, because the first list is why learning one of these transfers and the second
is why assuming they're the same bites.

**Generalises to all four:**

- A certificate is a claim; a signature over a fresh challenge is a proof. Never confuse them.
- Verification terminates at something you possessed beforehand. That part is configuration,
  not cryptography, and it is where the security actually comes from.
- The bytes are the signed object. You may repair an anchor; you may never repair something
  whose signature you check.
- `issuer` is a hint, the signature is proof.

**Does not generalise:**

- **What the names mean.** A DNS name, a person, nothing at all, free text — four schemes, four
  answers, and name semantics are never in RFC 5280.
- **Whether a chain exists.** §3.4 has none.
- **What expiry implies.** Load-bearing in two, a formality in one, deliberately ignored in the
  fourth.
- **What a successful verification licenses.** "The chain is valid" means a different sentence
  in each column of §3.5, and writing "certificate verified" in a log records none of them.
